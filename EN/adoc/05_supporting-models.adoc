== Supporting Models

ifdef::req42help[]
[role="req42help"]
****
.Content
Any kind of model – usually represented graphically, e.g. as diagrams, sketches or wireframes – that helps to understand backlog items and how they relate to each other. These representations should be linked to items in the Product Backlog.

.Motivation
In the agile world, it has become widespread to write requirements in the form of epics, features or user stories on little cards or to file them in equivalent form in tools.

Nevertheless, communication among all stakeholders sometimes becomes much easier if you also use the tools we have come to know over the last decades to make the colloquial language more precise. So don't be afraid to use models if they help communication.

Don't worry: these models don't have to be perfect. But especially with increasing complexity (loops or case distinctions), a graphical representation of the steps of a business process promotes understanding better than many tickets in the system without recognizable sequences and dependencies.

.Notations/Tools
* Flowcharts
* activity diagrams
* BPMN
* state diagrams
* data models (e.g. as ER or class diagrams)
* UI prototypes
* mock-ups
* wireframes

Suitable tools include simple drawing tools like Gliffy or Diagrams.net (formerly draw.io), text-based diagram languages like PlantUML (e.g. rendered via Kroki), or UML modeling tools like Enterprise Architect, Visual Paradigm or MagicDraw. The representations should be linked to your backlog items (in both directions).
